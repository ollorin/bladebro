<decisions>
Comment each where implemented (short "why" comments, AGENTS.md style).
- D5-1 Timestamp strategy = Rust-side duplicate-on-write at a constant rate (option a), NOT the sidecar's concat spool (option b). Why: frames arrive on stdin (requirement); concat needs every frame as a file on disk (spool dir, 0700, cleanup, and sensitive frames left on disk after a crash) and encodes the whole recording at stop (finalize grows with length and would break the 10 s bound; sidecar concat was already the slowest finalize at 562 ms). Mechanism: ffmpeg input `-f image2pipe -framerate <fps>` stamps the i-th JPEG at i/fps; `-fps_mode passthrough` makes ffmpeg keep every frame at that stamp (no dup, no drop: vfr was rejected in Phase 2 for dropping 566 of 800 frames); there is NO output `-r` (redundant under passthrough, and with a cfr mode it would let ffmpeg dup/drop on its own). So video duration = frames_written / fps exactly. Measured in planning on ffmpeg n9.0.2: 31 copies of a 1001x641 JPEG at `-framerate 10` -> ffprobe duration 3.100 s for both webm/vp9 and mp4/h264, output 1280x720, 31 frames read; passthrough and no fps flag gave identical files. The Pacer (Task 3) decides how many times each JPEG is written: slots(t) = round(elapsed_ms*fps/1000) cumulative from the first frame, writes = slots(now) - written, so rounding never accumulates (total error < 1 slot); frames faster than fps get 0 writes (that IS the fps cap); the final frame is held to the finish time and written at least once. Duration therefore tracks the timestamp span within 1/fps plus at most one forced final slot (3.1 s for a 3.0 s span at 10 fps = +3.3 %, inside the 10 % test bar).
- D5-2 VP9 `-crf 40`, not 36. RESULTS.md's recommendation table has no crf row; its measured VP9 numbers (870,778 B/min, 4.55 cpu-s/min at 10 fps 1280x720, 0 live drops) were produced by the sidecar builder at crf 40 (encoder.mjs line 62, 02-01-PLAN). 36 comes from pre-measurement research (STACK.md) and was never measured. Keeping 40 keeps the measured size/CPU numbers true for Phase 9's size-per-minute docs.
- D5-3 fps-mode flag gate: `-fps_mode` exists only from ffmpeg 5.1; Ubuntu 22.04 ships 4.4.2. `FfmpegVersion::Release { major <= 5 }` -> `-vsync passthrough`; Release major >= 6, `Git` and `Unknown` -> `-fps_mode passthrough`. `force_divisible_by` needs ffmpeg >= 4.3; older builds fail and that is reported honestly with ffmpeg's stderr (no special case).
- D5-4 Output safety: path must not start with '-' (checked first, explicit message), must be absolute (no cwd ambiguity; also makes ffmpeg treat it as a file, not a protocol), extension (case-insensitive) must equal `format.ext()`. Explicit muxer `-f webm|mp4` so the container never depends on the extension. `-y` is required: Phase 3 pre-creates the file 0600 with create_new; ffmpeg truncates it in place and the mode stays 0600 (measured); without `-y` ffmpeg would prompt and read the answer from stdin, which is the frame pipe.
- D5-5 `-hide_banner -nostats -loglevel error`: stderr carries only errors (the verdict tail); progress lines would only fill the 4 KiB tail. `-an` (no audio). Stdout unused (05-02 sets Stdio::null).
- D5-7 No new option, env var or config key in Phase 5. Timeouts, tail size, hold cap and flush interval are consts, not env-tunable (same rule as QUEUE_LEN, D3-5). docs/recording-and-launch-config.md gets only a short "how recording is encoded" note in 05-03.
- D5-8 classify precedence (first match wins): Killed -> Unfinalized; frames_written == 0 and no write error -> NoFrames (ffmpeg exits 234 "Output file does not contain any stream" with zero frames, measured; "no frames" is the honest cause); exit not Code(0) (code, signal or wait failure) -> ExitFailed; write error -> StoppedReading; bytes None or 0 -> EmptyOutput; else Finalized.
</decisions>

API: `pub const MAX_GAP_MS: u64 = 600_000;` (10 min: a single gap longer than this is a clock anomaly; idle pages are covered by the 05-02 progressive hold flush, which writes held frames every second, so the cap never shortens a real idle). `pub struct Pacer` (private fields: fps, started, last_ts, elapsed_ms, written, cur_written, clamped) with:
- `pub fn new(fps: u32) -> Self` (fps through `args::clamp_fps`).
- `pub fn on_frame(&mut self, ts_ms: u64) -> u64`: writes owed to the PREVIOUS pending frame. First call: start, return 0. Else gap = ts.saturating_sub(last_ts) (backwards = 0; last_ts = ts so a reset clock is followed, not frozen), clamp to MAX_GAP_MS (count clamped), elapsed += gap, n = slots(elapsed) - written (saturating), written += n, then cur_written = 0 (new pending frame).
- `pub fn advance_to(&mut self, ts_ms: u64) -> u64`: hold flush for the CURRENT pending frame without committing elapsed/last_ts: n = slots(elapsed + clamp(ts - last_ts)) - written (saturating; no clamp count); written += n; cur_written += n. Returns 0 before the first frame.
- `pub fn on_end(&mut self, end_ms: u64) -> u64`: like on_frame's gap step for end_ms (clamp counted), n = slots - written (saturating); if n == 0 and cur_written == 0 then n = 1 (the final visible state is always in the video); written += n. Returns 0 if no frame was ever seen.
