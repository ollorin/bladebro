<decisions>
- D9-13 Consts, not options (owner said "configurable? decide"): `DISK_LOW_MIB = 500` (>= 2 min at the max setting measured in Task 2 with a large margin; if the measured max rate x 2 min exceeds 500 MiB, raise the const to that value and say so), `MAX_DURATION = 2 h`, `MAX_FILE_BYTES = 1 GiB`. Reason: no drift-test registration, no schema/config surface, nothing for agents to read; documented in the docs and disk.rs. A user who needs longer splits recordings (stop/start).
- D9-14 `disk::free_bytes(dir) -> Option<u64>`: unix `df -k <dir>` (spawned with stdin null, short), `parse_df` = last line, field before the first `%` field, KiB*1024; Windows -> None. `HubEnv::free_bytes(&self, dir: &Path) -> Option<u64>` default body = disk::free_bytes; TestEnv returns a value from `Arc<AtomicU64>` (u64::MAX = unknown->None). None -> disk guard skipped for that tick (never a false stop).
- D9-15 Guard checks order per tick: browser lost / encoder dead (09-02), then disk low, then max duration (`Active.started.elapsed()`), then max size (`Tracker::files()` + `metadata().len()`, per file). Reasons map to texts in msg.rs: `stopped: disk low (<N> MiB free)`, `stopped: maximum duration (2 h) reached`, `stopped: size limit (1 GiB) reached`; they are FINALIZED outcomes (ok flag = finish verdict), parked in the orphan slot with prefix `previous recording ` -> e.g. `previous recording stopped: disk low (312 MiB free); saved: <path>`. Knobs gains `max_duration`, `max_file_bytes` (test-shortened).
- D9-16 Live idle: `BLADE_IDLE_TIMEOUT` (secs, checked every 15 s) is the real knob for both lanes; use 20 and wait up to 50 s. Disk low and the 2 h / 1 GiB limits are NOT driven live (never fill a disk; 2 h too long): unit-level with injected values, stated in the evidence.
</decisions>
