<decisions>
Comment each where implemented (short "why" comments, AGENTS.md style).
- D6-1 Own connection (Phase 2 verdict, user-binding): the recorder opens its OWN `CdpClient::connect` to the target's page WebSocket (`/json` lookup by target id via `cdp::discovery::list_page_targets`, an HTTP GET, not a CDP method), wrapped as `CdpSession::root`. It never uses `Page`'s session or event bus. Planner choice vs the sidecar's browser-WS + `Target.attachToTarget{flatten}`: the page WS is exactly how bladebro's own WS mode attaches a tab (`attach_tab_target`), needs zero `Target.*` methods (smaller allowlist) and binds by target id. Events on this connection are only ours (CDP events are per session), so no other subscriber ever sees a frame.
- D6-2 Pipe transport: `Endpoint::Pipe` (Phase 7 maps `crate::browser::launched_pipe()` to it) returns `SourceError::PipeTransport` before any I/O. No second flat session, no hacks (user decision). Verdict: `recording unavailable: BLADE_TRANSPORT=pipe has no debugging port for the recorder's own connection. Unset BLADE_TRANSPORT (the default WebSocket transport records), then run bladebro stop so the next launch uses it. Browsing is unaffected.`
- D6-3 Closed method set (SAFE-01): `pub enum RecMethod { PageEnable, StartScreencast, ScreencastFrameAck, StopScreencast }` with `as_str()`; the only send path is a private `send(RecMethod, params)` that also counts per method (`methods_sent`). No `&str` method parameter exists anywhere in source/. `Page.enable` is always sent before `Page.startScreencast` (Phase 2: attach without it failed with -32000 on a starting page). No `Page.disable`: closing the connection detaches the session.
- D6-4 Ack first: on each `Page.screencastFrame`, before parsing `data`, the handler takes `params.sessionId` (an integer, the screencast session) and the loop spawns the ack (`tokio::spawn` of `send(ScreencastFrameAck, {sessionId})` with ACK_TIMEOUT = 2 s; results counted into `acks_ok`/`ack_errors` via atomics, handles kept in a `JoinSet` so stop can await them within the grace). `acks_sent` is incremented when the ack is issued. If a frame arrives without `params.sessionId` (only possible above the 8 MiB hook cap, which strips params), the last seen screencast sessionId is used (counted `acked_with_cached_id`); with none known it is counted `unacked`. Invariant: `frames_received == acks_sent + unacked`.
- D6-5 Never block the reader: the CDP reader task only `broadcast::send`s (never blocks); the recorder task is a bus subscriber that does no await between receive and hand-off except the select itself. Hand-off is `FrameSink::send_frame` = `Encoder::send_frame` (try_send into the encoder's bounded queue, default 16 = `QUEUE_LEN`); `false` = newest frame refused, counted `queue_dropped`. `RecvError::Lagged(n)` adds n to `lost` (those frames were also never acked; Chrome's 2-frames-in-flight rule keeps this connection's bus to a few frames, so Lagged is practically unreachable; it is counted, not hidden). `Closed` ends the loop with `SourceOutcome::ConnectionLost`.
- D6-6 fps cap with newest-wins and trailing flush (`FpsGate`, arrival-time ms from a monotonic `Instant` base): interval = 1000 / clamp_fps(fps). A frame arriving >= interval after the last forward is forwarded now; otherwise it REPLACES the held frame (the replaced one is counted `capped`). The loop arms a timer for `last_forward + interval`; when it fires with a held frame, that frame is forwarded. At stop the held frame is forwarded (the final visible state always reaches the encoder). Base64 is decoded only for forwarded frames (held frames keep the base64 `String`), so decode cost is <= fps per second.
- D6-7 Timestamps for the Pacer: `ts_ms = round(metadata.timestamp * 1000)` (CDP TimeSinceEpoch seconds). Missing/non-finite/negative -> `SystemTime::now()` epoch ms (same clock domain), counted `ts_fallback`. A held frame keeps its own capture timestamp when forwarded later.
- D6-8 The hook (smallest form, user-binding): in `src/cdp/client.rs` add `pub(crate) const MAX_SCREENCAST_EVENT_BYTES: usize = 8 * 1024 * 1024;` directly under `MAX_EVENT_BYTES` (doc comment: fork hook, HOOKS.md; screencast frames are base64 JPEGs routinely far above 16 KiB and their `data` + `params.sessionId` are what the recorder needs; only a connection that started a screencast receives them, and Chrome keeps at most a couple unacked, so retention stays bounded; 8 MiB covers a 3840x2160 q100 JPEG with margin) and change the condition in `route_cdp_text` to `if text.len() > MAX_EVENT_BYTES && !(ev.method == "Page.screencastFrame" && text.len() <= MAX_SCREENCAST_EVENT_BYTES) {`. Nothing else in client.rs changes. tungstenite's default max message (64 MiB) and the pipe reader's 64 MiB limit are both above the cap.
- D6-9 No new option, env var or config key in Phase 6. ACK_TIMEOUT (2 s), STOP_GRACE (500 ms), the 8 MiB cap and the queue length are consts; `SourceConfig` fields exist so tests can shorten them and Phase 7 can pass the resolved RecordConfig.
</decisions>
