HTTP responses from `/json*` get `127.0.0.1:CHROME_PORT` rewritten to `127.0.0.1:LISTEN_PORT` (fix Content-Length); after a `101` upgrade, client->server frames are unmasked (RFC 6455 framing incl. 16/64-bit lengths, fragmentation) and each text frame's JSON `method` is appended to LOGFILE; server->client bytes are passed through untouched. Run the one-shot CLI `--host 127.0.0.1 --port LISTEN_PORT` (check the exact attach flags in `bladebro help`) for a fixed sequence: `nav $FIX/a.html`, `see content`, `state tabs`, `state cookies`, `state ls`, `act` click on a fixture element if a.html has one (else `see` again), against a Chrome launched by a daemon (`bb_port`). Compare sorted method multisets; settle/poll loops may vary counts, so the bar is: identical set of distinct methods, and no method in the new run that is absent in the base run; `Page.startScreencast`, `Page.screencastFrameAck`, `Target.getTargetInfo` beyond the base count are failures. If the proxy cannot be made to work in reasonable time, record the exact blocker and fall back to research section 7 items (1)-(3), saying plainly that the byte-level trace was not done.
