## Summary

The Phase 8 follower knows nothing about openers. It polls `GET /json` every 200 ms and follows the FIRST page of Chrome's list (`Rule::ListOrder`, pick.rs), confirmed on two samples 50 ms apart, and a brand-new tab must stay first for 1.5 s (`NEW_TAB_CONFIRM`, run.rs:319-341) because Bladebro re-fronts the opener after a click that opened a tab (page/mod.rs:597-619). `/json` has NO `openerId` (live: keys are only description, devtoolsFrontendUrl, id, title, type, url, webSocketDebuggerUrl; no `attached` either).

The recorder's own page WebSocket CAN see openers with zero page-visible effect: `Target.getTargets` and `Target.setDiscoverTargets` both work on a page-level connection and return/emit `openerId`, `canAccessOpener`, `attached`, `type`, `url` (measured). Neither is in `RecMethod` (wire.rs), so the closed set must grow from 4 to 5 or 6 methods (a deliberate Phase 6 SAFE-01 change, with its test).

**The finding that changes the plan:** a tab-style popup (target=_blank link, `window.open` without features) is `visibilityState=hidden` as soon as the opener is re-fronted, and a hidden tab delivers 0 screencast frames. Bladebro re-fronts the opener (Page.bringToFront) after every click that opened a tab. So observation alone can never put those popups in the video, and ROADMAP criterion 1 (as worded) is not reachable without either (A) skipping that re-front while recording (one upstream hook, behavior change under recording) or (B) the recorder calling `Target.activateTarget` on the popup (page-visible: it hides the opener, and the agent's next input action re-fronts the opener again). Window-feature popups stay in front and are already followed (08-02 measurement, 3.7 s for a click at ~1.5 s).

**Primary recommendation:** replace the 1.5 s new-tab guess with opener facts from the recorder's own page WS (Target events + getTargets), follow a popup as soon as it is also the front tab, return to the opener on close, report hidden popups honestly, and mark agent vs video in `state tabs` and the stop report. Put the A/B decision to the owner before planning 08.1-01 (default recommendation: neither; document and report honestly, see section 6).

## 1. Current follower (answers Q1; code read)

- Detect: `TabProbe::Http` = `list_page_targets` (discovery.rs:81, `GET /json`, devtools:// removed). Rule `ListOrder` = first page. `Confirm::feed` needs the same candidate on 2 samples (second after `CONFIRM`=50 ms). Known tab: switch after ~250 ms. Never-seen tab (`!known.contains`): must remain head for `NEW_TAB_CONFIRM` 1.5 s (so ~1.5-1.75 s delay, plus rebind ~10 ms). `Baseline` ignores a head that already differed at record-start.
- Gone: `!present || src.is_finished()` -> rebind to `agent_tab(list)` = list head with note `tab X gone at T s; following tab Y` (run.rs:299-313). Nothing remains: failure `no tab`. Probe errors x3: `lost`.
- Per-tab mode uses the same decisions; `Policy::enter` picks/creates the file (cap 8, `files.rs`).
- Why popup behaviour is partial today (08-02-popup-measure.txt, 08-03-FIXES.md): link popups were never followed (opener re-front wins within the 1.5 s); window-feature popup was followed at +2.2 s and no return was observed because it never closed.
- `state tabs` (state.rs:244-282): `Target.getTargets` on the AGENT session, marker `*` = `hub::is_current(tab.attached, id, own)`, where `own` = `Target.getTargetInfo` of the agent session while recording (hub.rs:96-109). Therefore `*` = the agent's tab, never the video's tab. This is the Phase 8 mismatch.
- Bladebro never moves its own `Page` to a popup (page/mod.rs:590-619; tools.rs:43 "switch-tab explicitly").

- Without any opener re-front (stock Chrome behaviour) the tab-style popup is visible, opener hidden, 1 frame (static page) in 1.2 s. After the opener's `bringToFront` the popup is hidden and 0 frames. `Target.activateTarget(popup)` from the browser connection makes it visible again (1 frame) and the opener hidden.
- On popup close, `/json` head returned to the opener in all 4 kinds (300 ms later); the page-WS got `targetDestroyed`.
- Event timing: `targetCreated` arrives in the same tick as the popup; `/json` shows it within 150 ms. Detection by event is ~10 ms, by poll <=200 ms.
- Allowlist: `RecMethod` has 4 variants (Page.enable, startScreencast, screencastFrameAck, stopScreencast), `ALL` + `closed_set_names` test (wire.rs:16-110). Adding `TargetGetTargets` (and `TargetSetDiscoverTargets` for events) is a 2-line enum change plus the test. Browser-level connection is NOT needed. These are browser-process-side, no Runtime/Emulation, nothing page-visible. The CDP-method comparison (SC5, recording off) is unaffected because the methods exist only inside the recorder. Event path: `route_cdp_text` and `Handler::on_recv` (handler.rs:93-104) currently ignore non-screencast events; `Target.*` events need a small branch (new pure fn, new file in `src/record/source/`, no cdp/client.rs change expected since they are small).

## 3. Recommended detection design (answers Q4a)

Add `Opener` knowledge to the follower as a pure, table-tested layer (new file `src/record/hub/follow/opener.rs`):

1. The CURRENT source's connection also yields `TabInfo{id, opener, can_access, url}` rows: poll `Target.getTargets` on it each tick (next to `/json`), or consume `targetCreated`/`targetDestroyed` events. Prefer poll-per-tick + events as accelerator: poll is robust to a source rebind (a new source starts with a fresh discover subscription; events fired between sources are lost; getTargets is stateless). One extra tiny CDP round trip per 200 ms tick.
2. `descendants(bound_chain)`: a page is a "popup of the recording" when its `openerId` is the current recorded tab, or any tab visited so far in this recording (follow the chain; treat a missing opener as an orphan of the most recent bound tab).
3. Candidate rule (replaces `NEW_TAB_CONFIRM` special-casing):
   - new tab with NO openerId (open-tab/`Target.createTarget`): follow when it is `/json` head on 2 samples (~250 ms), no 1.5 s wait.
   - new tab WITH an openerId in the recording chain: follow when it is `/json` head and stays head for `POPUP_SETTLE` = 800 ms (opener re-front measured ~0.6 s in 08-01; tab-style popup hidden = no frames, so following it before the re-front would flash one segment for nothing). Bound delay for a window-feature popup: <= ~1.1 s measured target (was 2.2 s); document the measured number from the live scenario.
   - head is a tab with an opener outside the chain: ignore as today (unrelated tab).
   - burst: while several new popups of the chain exist, the candidate is the one that is head (newest, measured order newest first). Intermediate popups that never held the front get NO segment; the stop report notes `N popups not followed (hidden behind the opener)` with ids (honest, bounded 1 line).
   - blocked popup: no target, nothing happens; test asserts zero segments and no note.
4. Hidden-popup honesty (tab-style popups after the opener re-front): the follower keeps the opener segment and counts `popup_hidden` (new target with chain opener that never reached head within 3 s). Add to the stop note: `popup <id> opened at T s was hidden behind the agent tab (not recorded; switch-tab to record it)`. This is consistent with Bladebro's documented behaviour and with SC1 as rewritten (see decision D1).

## 4. Return-to-opener on close (Q4b)

Rule: when the followed tab disappears from the list (or its source finished) the candidate is, in order, (a) its `openerId` if that page is still listed and in the chain, (b) the tab visited before it (previous segment's tab) if still listed, (c) list head (today's rule). Measured: Chrome already puts the opener first in `/json` after close, so today's head rule works for the plain cases; (a) matters when another tab is head (burst, popup opened from a non-head tab) and for a chain (grandchild closes: its opener, not an unrelated head). The note changes to `popup X closed at T s; back on opener Y`. Closing the recorded popup must never end the recording: reuse the `gone` path (run.rs:299-313; no `no_tab` failure while the opener lives). Per-tab mode: the opener's file is re-entered (same file, `Policy::enter`), as for switch-back today.

Also unchanged and needed: `Source::is_finished()` still triggers the rebind for the case where Chrome closes the socket before `/json` updates.

## 5. Agent-vs-video marker design (Q4c)

Facts: the ListTabs hook (state.rs:259-268) is 2 lines of logic and calls `hub::own_target` + `hub::is_current` (both in src/record/hub.rs, fork-owned). Everything else can change without touching upstream again, because the marker text is produced by `hub::is_current` (returns bool today).

Design (stays inside the existing hook, +<=3 upstream lines, listed in HOOKS.md as a Phase 8.1 row):
- Change `is_current` to a `hub::tab_marker(...) -> &'static str` (fork-owned) used in the same hook line. While recording, `own` = agent session target (as today) and `video` = `Tracker::current_tab()` (snapshot, no await on follower). Marker: `*` agent's tab; `R` the tab the video follows when it differs from the agent's; `*R` when the same tab. Without a recording: exactly today's `*`/space (CTRL-01 off path byte-identical, assert in a test).
- Footer line only when they differ: `(* agent, R video: differ; switch-tab to move the agent)`. Not added in the common (same tab) case, to keep tokens down (users are LLMs; AGENTS.md).
- Stop report: segments already list `[offset s tab id]`; add one note only if at stop the agent's tab differs from the last segment's tab: `agent was on tab A at stop; video followed tab B`. Agent tab at stop is already passed as `hint` (`Tracker::stop(hint)`).
- This documents (not hides) Bladebro's opener-stays-current behaviour, which ROADMAP SC3 explicitly allows.

## 6. Decisions the owner must make before planning (risks first)

- **D1 (blocking, CAPT-06 SC1 wording).** Tab-style popups are hidden (0 frames) after Bladebro's opener re-front, measured. Options: (0) recommended default: observe-only; they become a segment only if visible (window popups, or after `switch-tab`), hidden ones are reported honestly; rewrite SC1 to say so. (A) one upstream hook in page/mod.rs:597-619 to skip `self.activate()` while recording is active: popup stays in front like stock Chrome and is recorded; the agent's next input action re-fronts the opener (page/mod.rs:524-526) and the video returns after ~250 ms. Costs: a behaviour change under recording (opener hidden until the next action; throttled timers/rAF), 1 hook, and `act` verdict text still says opener active. (B) recorder `Target.activateTarget`: rejected, page-visible and races with the agent's `activate()`.
- R1: `Target.getTargets` result includes chrome:// `browser_ui` rows and extension background pages (seen); filter `type=page` and `http(s)|about|file` scheme as `/json` code does.
- R2: Chrome reported the grandchild's opener as the original opener after the middle popup closed (one run); the return rule must not assume a stable chain; keep fallback (b),(c).
- R3: headed Chrome and Linux/Windows popup foregrounding were not measured (08-01/08-02 also headless macOS only). The settle value must be re-measured per platform; keep `POPUP_SETTLE` a const next to `POLL`.
- R4: per-tab mode: a burst of N hidden popups must not create N files with 0 frames; create a file only when a popup is actually followed (becomes head and settles), and keep the 8-file cap note. Dormant popup files freeze (documented Phase 8 behaviour).
- R5: Source rebind loses `Target.setDiscoverTargets` subscription: use getTargets polling as the source of truth.
- R6: `RecMethod` growth is a SAFE-01 change; update `closed_set_names`, `idx`/`counts` array size (`[u64; 4]` in wire.rs:48,81) and the docs CDP-method list.
- R7: Cross-origin popup gets its own target id and keeps `openerId`; same-process navigation keeps the socket (Phase 6), cross-origin swap of the SAME tab remains handled by the generic gone/rebind path.
- R8: upstream hooks: aim for 1 new line in state.rs (marker) and at most 1 in page/mod.rs (only if D1=A); update HOOKS.md.

## Common Pitfalls

1. Following a hidden popup: video freezes on the last frame with a clean-looking segment. Gate on `/json` head + settle, never on opener alone.
2. Event-only detection misses popups created between two sources (rebind gap). Poll getTargets.
3. Ping-pong: popup followed, agent acts, opener re-fronted, rebind back, popup re-fronted by next click. Settle + `Confirm` already damp this; test a click-act-click loop.
4. A burst of 3 clicks: only the head is followed; do not queue segments per popup.
5. `state tabs` marker must stay byte-identical when not recording.
